### 5. 代码签名调研 —— 结论是**先不做**

| 方案 | 成本 | 要点 |
|---|---|---|
| SignPath Foundation | 免费 | 需公开仓库 + OSI 许可 + 项目活跃度审核；验项目不验人 |
| Azure **Artifact** Signing | $9.99/月（5,000 次） | 2026 年由 Trusted Signing 改名；云端密钥，无需硬件 token |
| 传统 OV / EV | $200–700/年 | **2023-06 起私钥必须存硬件**（token / HSM）；OV 需靠下载量攒 SmartScreen 声誉 |

Tauri 2 的接法在 `tauri.conf.json` 的 `bundle.windows`：
`certificateThumbprint` + `digestAlgorithm` + `timestampUrl`（CLI 自动调 signtool），
或 `signCommand "... %1"`（`artifact-signing-cli` / `relic`）。
**三个坑**：必须加时间戳（否则证书过期后旧包签名失效）、签 MSI 必须传 `-d`（否则 UAC 显示随机字符）、
签完用 `signtool verify /pa` 验证。已写进 README 的 Roadmap。

## 三、进度 / 日志子系统的结构（下一个改动这里的人必读）

### 谁在发进度事件

只有 4 处：`ftp/client.rs`、`sftp/client.rs`、`sftp/server.rs`、`tftp/client.rs`。
**TFTP 服务端不发**（只打 tracing 日志）；FTP 服务端（libunftp）也不发。

### 页脚是单槽位 —— 能不能并发，看来源

`App.tsx` 只有一个 `progress` state，事件直接覆盖（后到者赢）。

| 场景 | 并发? | 原因 |
|---|---|---|
| FTP / SFTP 客户端连传两个 | 否 | `AppState.ftp_client` / `sftp_client` 是 AsyncMutex，**命令全程持锁**，第二个排队 |
| **两个 TFTP 传输** | **是** | AppState 里**没有 tftp_client 槽位**，`tftp::put/get` 无状态、每次新开 UDP socket，完全没串行化 |
| 回环（GUI 客户端连自己的 SFTP 服务） | 是 | 客户端 + 服务端各发一路，同 kind 同 file id（审查 #8） |
| 外部客户端下载 + GUI 客户端上传 | 是 | 服务端事件 + 客户端事件撞车 |

### 如果要支持多个并发传输

- **页脚改多槽位：小活**（约 3 文件 80–120 行，纯前端）。事件自带 `kind` + `file`，天然可当 key；
  后端**零改动**。回环撞车可在 `lib.rs::progress_forwarder` 里给 payload 加 `source` 标记
  （约 10 行，不必动引擎的 `TransferEvent` 和 26 个 emit 点）。
- **但让 FTP/SFTP 客户端真能并发传：大活**。现在一个客户端一条连接、全程独占，
  要并发就得改连接管理（连接池 / 每传输一条连接），涉及 AppState 槽位、
  每个命令的加锁方式、SFTP 的 TOFU 状态与 FTP 的 SIZE/数据通道冲突。**别顺手做，先出方案。**

### 实现细节（踩过的坑）

- 进度 handler 用 `progressRef` 镜像 state —— 该 effect 依赖是 `[log]`、只构建一次，
  闭包里的 `progress` 是**过期**的；速度和耗时都必须读 ref。
- 事件里的文件与当前不符时**要重开一个样本**，不能把字节数并进上一个文件的速率
  （回环两路事件共用槽位时会产生荒谬的速度尖峰）。
- `%` 格式化的（Display）tracing 字段走 **`record_debug` 而非 `record_str`**，
  但 `DisplayValue` 的 Debug 转发 Display（`tracing-core/src/field.rs:728`），
  所以 `format!("{value:?}")` 拿到的是**不带引号**的字符串，无需剥引号。
- 速度**不能**用原始 per-event 差值直接显示：跳得没法读，一次卡顿就报 0 B/s。

## 四、本机环境新增的一条坑

**`cargo check` 可能撞 rustc ICE**（`encode_metadata` 里 `option::expect_failed` panic）。
**不是代码问题**——是 target 目录的 incremental 缓存被杀软锁坏（伴随熟悉的 `os error 5`）。

```bash
CARGO_INCREMENTAL=0 cargo check -p ftp-core     # 即通过
```

遇到 ICE 先怀疑增量缓存，别去改代码。

其余环境坑（杀软 `os error 5`、GUI 白屏需 `--no-sandbox`、系统 `sftp.exe` 不可用、
`wmic`/`reg.exe` 被拦）见 `MEMORY.md` 与前两篇交接。
