# 代码审查标准与流程

本文件是 ftp-toolbox 的**成文审查机制**：严重度怎么分级、审查在哪些节点发生、
覆盖到什么程度算够、发现如何编号与闭环。2026-10-08 之前审查分级只隐含在
`deliverables/software-company/` 的各报告里，本文件把它固化为仓库规则，
后续审查（人工或 AI 评审）均以此为基准。

## 严重度分级

| 级别 | 标记 | 判定标准（任一命中即归入该级） | 处置要求 |
| --- | --- | --- | --- |
| Critical | 🔴 | 数据丢失或损坏（如 known_hosts 半写）；协议应答**误导对端**（如 0 长度 READ 回 EOF）；匿名可达的安全漏洞（如无防护的 PORT bounce 跳板）；发版产物损坏或版本错乱 | 立即整改，整改完成前**不得发版** |
| High | 🟠 | 常见路径功能失效；静默丢数据（IPC 漏 `#[serde(rename_all = "camelCase")]` 这类不报错的错）；有实际触发条件的竞态 | 本轮内整改，附回归测试 |
| Medium | 🟡 | 边缘路径错误但有兜底；文档与代码事实漂移（如版本同步清单少一处）；资源泄漏（有界的） | 限期整改，记录跟踪 |
| Low | 🟢 | 观感、文案、命名、不影响行为的顺序问题 | 记录即可，可延后 |

**优先级顺序**：功能正确性 > 安全 > 性能 > 可维护性 > 一致性。

## 审查节点

1. **提交前自查**（每个提交）：`cargo test -p ftp-core`、`cargo check --workspace`、
   `cd app/ui && npm test && npm run typecheck` 全绿；提交信息符合 Conventional Commits（英文）。
2. **合入前评审**（代码提交）：改动逐文件过一遍本文件的「红线清单」。
   单人仓库没有第二双眼睛时，**必须在下一轮审计补齐**，不允许无限期跳过。
3. **发版门禁**（每次出包）：
   - 测试全绿（同上四条命令）；
   - 版本号 **5 处同步**（见 `CONTRIBUTING.md`「版本号」）；
   - exe `CompanyName` / MSI `Manufacturer` 为 **halacrcrc**；
   - 改动涉及安装器配置（tauri.conf.json、license、图标）时，先在干净目录实装验证。
   - **先提交再发版**：安装包一旦上传 GitHub Releases，对应源码必须已在 main 上——
     否则该版本无法从仓库复现。
4. **阶段性审计**（事后补审）：对「发版后仍未评审」的提交做一轮集中审查，
   报告归档 `deliverables/software-company/code-review-<日期>.md`。

## 覆盖率要求

- 代码提交：**逐文件审查**，不以抽样代替。
- 新行为必须被测试钉住（如主动模式开关：开启正向 + 关闭保持拒绝，两例都要）。
- 纯文档提交走轻量路径：核对每条**可验证断言**与代码事实一致即可
  （例：声称「5 处同步」就去数是不是 5 处；声称某上游行为是死代码就去读上游源码）。
- 审查证据（命令输出、md5、逐字节比对）写入报告，保证结论可追溯。

## 发现编号与闭环

- 每轮审查的发现按 `#N` 编号（跨轮不重复使用，标注日期区分，如「2026-09-30 #11」）。
- 报告归档后，整改走独立的 `change-report-<主题>-<日期>.md`，逐条对应发现编号。
- 整改后**复验**：重跑相关测试并在报告里记录结果，未复验的整改不算闭环。
- 明确「不修」的发现也要记录理由与影响面（如单槽位页脚的同向回环折样），
  归入设计文档的已知取舍，而不是消失。

## 审查报告模板

新报告复制以下骨架（与既有 `deliverables/software-company/code-review-*.md` 风格一致）：

```markdown
# 代码审查 <范围>（<日期>）

## 审计范围与方法
（提交区间 / 文件清单 / 用了什么验证手段）

## 整体评估
✅ / ⚠️ / ❌ —— 主要优点与关键风险，不超过 3 句。

## 发现清单（按严重度排序）
### <#N> <标题>（🔴/🟠/🟡/🟢）
- 位置：`<file>#L<start>-L<end>`
- 分析：根因与影响。
- 修复建议：原代码 / 改进代码对照（必须可直接落地）。

## 验证结果
（cargo test / npm test / typecheck / check --workspace 的实际输出摘要）

## 逐提交结论（如为区间审计）
| 提交 | 类型 | 结论 |
```

## 红线清单（审查时逐条过，均有历史教训）

- IPC 结构体是否标 `#[serde(rename_all = "camelCase")]`（漏标 = 前端静默读 undefined）。
- `app/ui/src/lib/*` 相对 import 是否带 `.ts` 后缀；被测模块是否 import 了 `api.ts`。
- JSX 里 `{expr}` 后紧跟换行的空白剥除（`{join("、")}` 与后续汉字必须同行）。
- 服务端生命周期：bind-first、停止走 `broadcast::Sender` + `handle.stop().await`、
  状态推送用 `send_replace`、`*_server_status` 是前端状态唯一来源。
- 引擎纯函数边界：壳层不得重写 `passive.rs` / `net.rs` 已有的纯逻辑。
- `prefs.iface` 是否被运行时改写（只允许告警，不允许静默写回）。
- FTP 主动模式开关保持默认关闭（libunftp PORT 无 bounce 防护）。
- rcgen 依赖保持 `default-features=false, features=["pem","aws_lc_rs"]`。
- 升版本 5 处同步；图标三份派生物一起重导。
- 别整体 `cargo fmt`（基线本就不是全绿，见下）。

## 基线豁免与非目标

- `cargo fmt --check` 与 `cargo clippy -p ftp-core --all-targets` **基线即红**：
  本机制只要求新增/修改代码对齐，不要求全仓转绿，禁止顺手整体 fmt 产生无关 diff。
- CI 自动化门禁（GitHub Actions / PR 模板）暂缓：单人直推 main、无 PR 流，
  且本机到 github.com 的网络不稳定。待协作规模变化后再立项，届时需先固化
  fmt/clippy 基线豁免清单，否则门禁无法区分新引入问题与存量问题。
