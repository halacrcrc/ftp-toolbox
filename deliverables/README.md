# deliverables

**这里不是源码。** 存放的是本项目的工程过程产物：代码评审报告、交接文档、
QA 验证记录、故障诊断，以及配套截图 / 脚本。放在版本库里是为了让结论可追溯
（评审说了什么、哪次验证发现了什么、某个坑的根因是什么），而不是为了发布。

如果你只是想知道这个项目怎么用 / 怎么构建，看仓库根的 [README](../README.md) 就够了。
项目的**设计规格与决策记录**在 [`docs/`](../docs/)，那才是长期有效的文档；
`deliverables/` 里的东西大多带日期，属于**历史快照**，可能已经过时。

## 目录结构

### `software-company/`

评审、交接、验证、诊断类报告。文件名多为 `<类型>-<主题>-<日期>.md`。

| 类型 | 说明 |
| --- | --- |
| `code-review-*.md` | 代码评审结论（含发现分级与整改对应） |
| `handoff-*.md` | 交接文档：当前进度、待办、踩坑配方 |
| `qa-verification*.md` | QA 验证轮次记录（含复现步骤与证据） |
| `change-report-*.md` | 整改变更报告 |
| `*-diagnosis.md` | 具体故障的根因诊断（端口占用、网卡刷新等） |
| `transfer-speed-log-*/` | 进度条 / 日志子系统的实测截图 |

### `sftp-gui-integration-2026-09-29/`

SFTP 的 GUI 端到端联调记录：截图 + 驱动脚本（`gui-e2e.mjs`、
`webview-watch.py`、`dump-parse.py`）。脚本可复现当时那轮联调。

## 约定

- **文件名带日期**，同一主题的多次迭代靠日期区分，不要覆盖旧文件。
- 报告里出现的本机绝对路径（如 `C:\Users\...\build\...`）是**当时的实测证据**，
  保留原样以便追溯，不代表项目要求这些路径。
- 新报告请按上述命名归入 `software-company/`；纯截图放同名子目录。
